一、 底层架构升级方案
1. Node.js 运行时与核心环境升级

    升级 Node.js 20/22 LTS：将项目的基础运行时升级到现代 Node.js LTS 版本，获得更好的 V8 引擎性能、较低的内存占用以及对现代异步 API 的良好支持。

    剔除原生 C++ 构建依赖：彻底移除 leveldown 等老旧依赖。构建 Docker 镜像时不再需要安装 python3、make、g++ 等重型编译工具链，使 Docker 镜像体积从 300MB+ 缩减至 60MB 左右，构建时间由数分钟缩短至几秒。

2. 缓存架构替换（方案一：纯内存缓存）

    引入 lru-cache 机制：采用 LRU（最近最少使用）算法的纯内存缓存服务。

    防刷与高效读取：根据路由和请求参数生成唯一的缓存 key，将生成好的 RSS XML 或微博 Raw 数据存入 Node.js 进程内存中。对于频繁被 RSS 阅读器刷新的订阅，直接从内存中秒级返回，彻底避免对微博 API 进行不必要的重复请求。

    自动过期清理：针对 RSS 场景设置 15~20 分钟的默认缓存过期时间（TTL），超过时间的条目会被自动移出内存，兼顾数据实时性与内存控制。

二、 抗风控与防封禁强化方案

为了解决微博 API 极其严格的风控限流（如 403、418 报错或要求输入验证码），从网络请求层引入以下 5 大防御策略：
1. 动态生成与轮换“访客 Cookie”

    在发起数据请求前，自动调用微博官方的访客身份生成接口，获取临时的身份标识（sub 和 subp Cookie）并存在内存中使用。

    当触发限流或 Cookie 到期时，自动清空并重新申请一组新的访客 Cookie。

2. 真实浏览器 Request Header 伪造

    固定 Chrome/Safari 移动端 User-Agent：放弃使用 HTTP 客户端默认的标识，使用现代真实移动端浏览器的 User-Agent。

    补全关键标头：按真实浏览器标准补充 Referer（如指向 [https://m.weibo.cn/](https://m.weibo.cn/)）、Accept-Language 等字段，使请求指纹与普通用户刷微博行为保持一致。

3. 个人账号 Cookie 兜底支持

    提供环境变量配置选项（如 WEIBO_COOKIE）。

    系统优先判断是否存在用户配置的个人 Cookie；若存在则优先使用。在个人自用场景下，使用登录后的 Cookie 可以实现近乎 100% 的抗封禁与稳定抓取。

4. 并发请求去重（Request Collapsing）

    当 RSS 阅读器短时间内发起多个相同路由的并发请求时，网络层会锁住当前正在进行中的异步请求，让后续相同 URL 的请求共享同一个返回结果，避免短时间向微博服务器发出重复请求而触发风控。

5. 指数退避与自动重试

    当请求遇到网络超时或非致命的状态码报错时，系统会自动暂停 1~2 秒并重新发起请求，提高抓取成功率，避免 RSS 阅读器直接抛错。

三、 总结效果

完成上述升级后：

    运维极简：项目只需一个标准的 Node.js 镜像或 Serverless 实例即可秒级运行，无需额外挂载数据库文件或配置 Redis。

    构建稳定：彻底告别 pnpm/npm 原生模块编译报错（如 ERR_PNPM_IGNORED_BUILDS）。

    高可用性：配合内存缓存与 Cookie 伪造，抓取微博数据的成功率和抗风控能力将获得大幅提升。
